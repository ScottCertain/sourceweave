## 1. Summary

SourceWeave is a generation-focused documentation system. It reads an open-source project's source code and releases, drafts documentation with AI, evaluates that output against a human-authored style guide and against the source of truth, and publishes the reviewed result as a Docusaurus site on Netlify.

The first target is AnythingLLM, an open-source AI application maintained by Mintplex Labs. SourceWeave is an independent, unofficial project and is not affiliated with or endorsed by Mintplex Labs.

## 2. Purpose and context

SourceWeave is a skills-building project in two disciplines:

- **Documentation automation**: designing a pipeline that turns source material into accurate, publishable documentation with AI doing most of the drafting.
- **Technical writing**: authoring a style guide from hands-on editing of generated output, and designing a way to measure whether automated output follows that guide and stays accurate.

The project doubles as a public portfolio piece, so the pipeline, style guide, evaluation harness, and commit history are all meant to be visible.

## 3. Goals

| ID | Goal | Status |
|---|---|---|
| G1 | Generate the majority of AnythingLLM documentation prose with an automated pipeline | Decided |
| G2 | Author a style guide, derived from reading and editing a meaningful share of generated output | Decided |
| G3 | Design an assessment that measures style-guide adherence and factual accuracy of generated output | Decided |
| G4 | Compare SourceWeave output against the official AnythingLLM documentation to find gaps and drift | Decided |
| G5 | Publish the docs with Docusaurus on Netlify | Decided |
| G6 | Keep the system product-agnostic so a second target project can be added without restructuring | Proposed |

## 4. Non-goals

- Contributing code or documentation changes upstream to Mintplex Labs.
- Copying or republishing content from the official AnythingLLM docs. The official docs are **read-only input** for comparison.
- Presenting SourceWeave as official, endorsed, or authoritative AnythingLLM documentation.
- Fully autonomous publishing. Generated content passes through evaluation and human review before release.
- Maintaining documentation for every historical AnythingLLM version.

## 6. Source inputs

| Input | Location | Role | Status |
|---|---|---|---|
| AnythingLLM code | `Mintplex-Labs/anything-llm` (primary branch: `master`) | Source of truth for behavior, settings, and API | Decided (read-only) |
| AnythingLLM release tags | Tags on the code repo (format `vX.Y.Z`) | Defines the version each docs build describes | Proposed |
| OpenAPI/Swagger spec | Generated by the AnythingLLM server (exact path to confirm) | Source for API reference generation and API drift checks | Proposed |
| Official docs | `Mintplex-Labs/anythingllm-docs` (MIT) | Comparison baseline for gap and drift analysis; not copied | Decided (read-only) |

**Integration method (Proposed):** add both upstream repos as Git submodules pinned to specific commits, with the code repo pinned to a release tag. Note that `anything-llm` contains submodules of its own (embed widget, browser extension); initialize recursively only if those components are in scope.

## 10. Success metrics

Thresholds are TBD and should be set after the first evaluation runs establish a baseline.

| Metric | Measures | Target |
|---|---|---|
| Style adherence score | Share of style rules satisfied per page | TBD |
| Accuracy score | Share of verifiable claims confirmed against source | TBD |
| Code sample pass rate | Share of samples that execute successfully at the pinned version | TBD |
| Human edit ratio | Share of generated text changed during review (should fall as the pipeline improves) | TBD |
| Release lag | Time from an upstream release to a published docs update | TBD |
| Coverage delta | Topics documented relative to the official docs | TBD |
| Indexing readiness | All metrics above at threshold, triggering removal of `noIndex` | TBD |

## 11. Milestones

| Phase | Scope | Exit criteria |
|---|---|---|
| **M0: Foundation** | Repo scaffold, licenses, README with disclaimers, `.gitignore`, Docusaurus site deploying to Netlify with `noIndex` | Empty site live on Netlify from CI |
| **M1: Upstream wiring** | Submodules pinned, release-watch workflow | New upstream release produces a bump PR automatically |
| **M2: First generation slice** | Generate one bounded section end to end (candidate: API reference from the OpenAPI spec) | Section published with provenance recorded |
| **M3: Style guide v1** | Edit the M2 output; write the first style guide from those edits | Style guide committed; initial rules machine-checkable |
| **M4: Evaluation v1** | Style and accuracy scoring; CI checks; baseline scores | Scores recorded for M2 output |
| **M5: Comparison** | Gap and drift reports against the official docs | First comparison report published |
| **M6: Expansion** | Additional content types and sections; stable and preview streams | Metric thresholds set and tracked |

## 12. Risks

| Risk | Mitigation |
|---|---|
| Generated content contains confident errors | Ground generation in pinned sources; accuracy scoring; execute code samples; human review; `noIndex` until quality is proven |
| Users mistake SourceWeave for official docs | Unofficial statement on every page; no Mintplex branding; no domain implying affiliation |
| Upstream changes quickly and docs fall behind | Release watching, `master` monitoring, and a limited version support policy |
| LLM costs grow with each regeneration | Per-run budget; regenerate only pages whose sources changed |
| Evaluation measures the wrong things | Calibrate automated scores against human judgment on a sample of pages |
| Copyright in AI-generated prose is unsettled | Disclose AI generation; rely on human editing, selection, and arrangement; revisit if guidance changes |
| Code repo license differs from expectations | Confirm the license in `anything-llm` before reading code into the pipeline |

## 13. Open questions

1. Which LLM provider and model(s) will the generation pipeline use, and which will the evaluation pipeline use? (Using a different model to evaluate than to generate may reduce shared blind spots.)
2. What language will the pipeline and evaluation harness use: Node/TypeScript to match Docusaurus, Python, or a mix?
3. How will accuracy be verified in practice: claim extraction and source lookup, executing examples against a Docker instance of AnythingLLM, or both?
4. Which documentation section comes first? (API reference is proposed because the OpenAPI spec provides a structured source of truth.)
5. What are the metric thresholds for removing `noIndex`?
6. What is the per-run LLM budget?
7. Will the preview stream from `master` be published from the start, or added after the stable stream works?
8. Confirm the license terms of the `anything-llm` code repo.
9. Confirm the location of the OpenAPI/Swagger spec in the AnythingLLM server code.
