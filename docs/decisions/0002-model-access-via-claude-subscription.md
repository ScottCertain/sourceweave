# 0002. Generation operates under a fixed capacity budget

**Status:** Accepted
**Date:** 2026-09-16
**Closes:** PRD §13 Q1, and reframes PRD NFR-3

## Context

The PRD asks which provider and models generation and evaluation should use, and leaves a per-run spend budget open (NFR-3). Both questions assume an elastic, metered resource: you decide how much to spend, and capacity follows.

This project makes the opposite assumption. Model access runs on a Claude subscription through the Claude Code CLI (`claude -p`), which has a **fixed capacity ceiling** — rolling 5-hour and weekly rate limits — and no marginal cost. The GitHub Action supports the same credential path through a `CLAUDE_CODE_OAUTH_TOKEN` secret generated by `claude setup-token`, so the constraint holds end to end, including CI.

The choice is deliberate, and not primarily about money.

A documentation pipeline that can spend its way through a full-corpus regeneration never has to answer the questions that make the work interesting: which pages are actually stale, what is worth regenerating, how a run survives being interrupted halfway through. A fixed ceiling forces those questions to be answered in the design rather than deferred. It is also the more common real-world constraint — most teams operate against a quota someone else set, not an open budget.

So the ceiling is treated as a design input, not an obstacle to route around.

## Decision

All model access goes through the Claude Code CLI in print mode. `pipeline/` and `eval/` shell out to `claude -p`; neither imports an Anthropic SDK, and neither reads `ANTHROPIC_API_KEY`.

- **Generation** uses the higher-capability tier (Opus).
- **Evaluation** uses a different tier (Sonnet) from generation.

A different tier rather than a different vendor is a compromise, and a real one. The PRD notes that a different evaluator may reduce shared blind spots; a different tier of the same model family reduces them less than a different vendor would. See Consequences.

### Load-bearing constraint: never use `--bare`

`--bare` skips auto-discovery and starts faster, and the Claude Code docs recommend it for scripted and CI calls. **It cannot be used here.** In bare mode Claude Code does not read OAuth credentials or the system keychain, and requires `ANTHROPIC_API_KEY` instead.

The reason this is a hard rule rather than a preference is the **failure mode, not the cost**: adding `--bare` does not raise an error. The run succeeds. It simply executes against a different credential path than the one this project is designed around, and nothing in the output says so. A silent change in which credential a pipeline authenticates with is worth a guard regardless of what it costs.

The guard is enforced in three places:

1. `claude_client.py` never emits `--bare`, and strips any inherited `ANTHROPIC_API_KEY` from the subprocess environment so a key set for an unrelated tool cannot redirect the run.
2. `pipeline/tests/test_claude_client.py::TestBillingInvariants` fails the build if either protection is removed.
3. `CLAUDE.md` states the rule for any agent working in the repository.

### Standard invocation shape

```
claude -p <prompt>
  --model <opus|sonnet>
  --output-format json          # result + client-side cost estimate + session id
  --json-schema <schema>        # evaluation only: structured scores
  --settings <pinned file>      # pin ambient config; see reproducibility below
  --permission-mode dontAsk     # unattended: deny anything that would prompt
  --permission-prompts none     # unattended: do not wait for a permission host
  --append-system-prompt-file <prompt version file>
```

## Consequences

### The capacity ceiling shapes the pipeline

**NFR-3 changes from a spend budget to a rate budget.** The number to manage is invocations per window, not dollars per run.

**Incremental regeneration is promoted from optimization to requirement.** The PRD lists "regenerate only pages whose sources changed" under §12 as a cost mitigation. Under a fixed ceiling it is not a mitigation — a full-corpus regeneration will exhaust the window long before it finishes. `provenance.py` records a SHA-256 per source file so staleness is a fact about the page, not a guess.

**Runs must checkpoint and resume.** Hitting the ceiling mid-run must be recoverable without redoing completed pages. `RateLimited` is a distinct exception type precisely so callers can checkpoint and stop cleanly rather than retry into a wall.

**Generation is local and supervised; CI invokes no model.** Reviewed output is committed (FR-8 already requires this), and CI lints, link-checks, and builds. This keeps rate-limited work under direct human supervision, where exhausting a window is an inconvenience rather than a red build.

### Reproducibility: a real gap, partially mitigated

This is the genuine cost of the decision and the place where it is weakest.

`--bare` exists for reproducibility. It skips discovery of hooks, skills, MCP servers, plugins, and ambient `CLAUDE.md`. Without it, a `-p` run loads whatever is configured in the working directory and in `~/.claude`, which means the machine contributes to the run. That is in tension with **NFR-2: builds are reproducible from a given commit.**

The tension is not fully resolved. It is narrowed:

- Settings are pinned in `pipeline/claude-settings.json` and passed with `--settings` rather than inherited. `ClaudeClient` refuses to construct if the file is missing, so a run cannot quietly fall back to ambient settings.
- Those settings also deny `Bash`, `WebFetch`, and `WebSearch`, which turns FR-4's grounding requirement into an enforced property rather than a prompt instruction: generation cannot reach the network, so it cannot describe anything but the pinned source.
- `CLAUDE.md` is version-controlled, so the largest piece of ambient context is pinned by the commit.
- The pipeline configures no MCP servers and relies on no skills.
- `Provenance.ambient_context` digests both inputs, so a page generated under different conditions is *detectable* even though it is not *prevented*.

`.claude/settings.json` is deliberately excluded from that digest. It governs interactive work, and Claude Code writes to it when a permission is approved; including it would report drift across every previously generated page whenever someone approved a tool by hand. The fingerprint tracks what governs *runs*, not what governs the repository.

What remains: a hook or MCP server in a contributor's `~/.claude` would still load, and provenance would record a changed digest after the fact rather than blocking the run. For a solo project this is acceptable. If the project gains contributors, revisit — the honest options are a documented environment requirement, or moving to an API key and accepting metered billing in exchange for hermetic runs.

### Evaluation independence is weakened

Same-family evaluation shares blind spots that a different vendor would not. The PRD's mitigation — calibrate automated scores against human judgment on a sample of pages — is therefore load-bearing rather than a backstop, and is treated as required work in M4, not optional polish. An evaluation harness never checked against human judgment produces numbers, not measurements.

### Other

**Cost is recorded but not billed.** `--output-format json` reports a client-side `total_cost_usd` estimate per invocation. Nothing is charged; it is stored in provenance as a proxy for run weight and as input to the quality-trend data in FR-15.

**CI needs a `CLAUDE_CODE_OAUTH_TOKEN` secret**, not an API key. The token is tied to one person's subscription — fine for a solo project, a known limitation otherwise.

**Provider coupling.** The pipeline depends on the Claude Code CLI's interface. Confined to one module, `pipeline/sourceweave_pipeline/claude_client.py`, so switching to an API or another vendor is a change to a single file.
